Overall Design:
Observer vs MVC
- MVC allows us to spawn in Model and View, we can use to control the game and handle communication between the two
- Observer is more messy but it has less code and less indirection as View will communicate directly with Model

Design Question 1:
How could you design your system so that each Arcanist class can be easily generated, and its class
ability cleanly applied without scattering conditionals throughout the codebase? How difficult does
such a design make it to add a fifth class later?

Design Pattern: Factory vs Decorator
Analysis: 
- With a base Arcanist, can make decorator representing class, which wraps Arcanist object and adds specific abilities
    - Problem is that client must control wrapping, which is not ideal -- we should have more abstraction 
- But factory can be used to simply take the requested Arcanist class, and return the right object instance -- doesn't require complex wrapping logic
    - Also, adding a 5th Arcanist class is simple as can just incorporate in if-conditional in Factory

With factory, we cannot combine classes, which is fine so decorator's advantage not needed here
With decorator, client must wrap the object that they want

Design Question 3:
How could you implement special abilities for Spectres, for example, Focus Point drain for Wraiths,
temporary Warding reduction for Banshees, or rune-fragment theft for Shades? What design pattern
best models abilities that modify combat outcomes without permanently altering the character objects
involved?

Design Patterns: Decorator vs Visitor
Analysis:

Decorator:
Advantage: You can decorate the attack action itself. When a Wraith attacks, it wraps its standard attack in a DrainFocusDecorator. This modifies the outcome temporarily without altering the Arcanist's base stats permanently.
Tradeoff: Creates many short-lived objects in memory every time combat occurs.

Visitor:
Advantage: You can implement a CombatVisitor. When the Arcanist attacks, they pass a visitor to the Spectre. The Visitor resolves the specific combat logic based on the Spectre's concrete type.
Tradeoff: If you add a new Spectre type later, you must update the Visitor interface and all its implementations.


Design Question 4:
What design pattern could you use to model the temporary effects of Surge Power, Fortify Ward, Sap
Power, and Erode Ward, so that you do not need to explicitly track which scrolls the Arcanist has
used on a given level? Consider how level transitions should trigger the reversal of these effects.

Design Patterns: Decorator vs Command
Decorator:
Advantage: When the Arcanist uses a Surge Power scroll, you wrap the Arcanist object in a SurgePowerDecorator. When transitioning to the next vault level, the Level Manager simply strips away all decorators, passing only the base Arcanist to the new level.
Tradeoff: Managing references can get tricky. Other objects need to know they are interacting with the decorated interface, not the base concrete class.

Command:
Advantage: Scrolls act as Commands with execute() and undo() methods. The Game Manager keeps a stack of active scroll commands. Upon level descent, it simply iterates through the stack and calls undo() on all of them.
Tradeoff: Requires building a robust invoker/history system, which might be more infrastructure than needed for simple stat buffs.


Design Question 5:
How could you design item generation so that Rune Fragments, Scrolls, and Major Items reuse as
much code as possible? How would you structure your hierarchy to avoid duplicating the 'guarded
placement' logic shared by the Shard Coffer and the Aegis Cloak?

Decorator:
Advantage: Create a GuardedItemDecorator that wraps any base Item (whether it is a Shard Coffer or the Aegis Cloak). The decorator overrides the pickup() method to check a reference to its specific Vault Anchor. If the Anchor is alive, the method fails.
Tradeoff: Very flexible, but requires passing the Vault Anchor reference into the item decorator at instantiation.

State:
Advantage: The guarded item has two states: LockedState and UnlockedState. It starts locked, and when the associated Vault Anchor dies, it transitions to unlocked, allowing the Arcanist to collect it.
Tradeoff: Requires maintaining state transition logic for items, which are otherwise mostly passive data structures.
